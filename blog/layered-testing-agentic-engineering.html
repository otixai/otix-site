Directing Agents to Test, Part 1: Layers and Principles

Define the behavior, choose the test boundaries, and make the agent prove the work is done.

Agentic Engineering Testing Spec-Driven

An agent can write code and tests that share the same mistake. Everything passes. The feature is still wrong.

I want tests that challenge the implementation. That starts with clear requirements and checks at different boundaries. This series shows how I would direct an agent through that work, using one example: inviting someone to a workspace.

Start With the Rule

Only an administrator of the target workspace may invite a member. An administrator in workspace A has no authority in workspace B.

An agent that checks only user.isAdmin can miss that distinction. Tests for “admin” and “regular user” will miss it too. Give the agent the cross-workspace case explicitly, including what must not happen: no invitation saved and no delivery queued.

Acceptance criteria define the expected behavior. Test scope defines how much of the system runs. An API test and a browser journey can check the same criterion while exercising different boundaries.

Give Each Layer a Job

For this feature, I'd divide the checks this way:

  • Static checks: catch invalid imports, types, and syntax before running behavioral tests.
  • Unit and property tests: explore role combinations, workspace membership, and expiration boundaries.
  • API acceptance tests: submit requests through the public interface and verify responses and side effects.
  • Integration and contract tests: exercise real persistence and verify what clients and services exchange.
  • UI and end-to-end tests: check the form, then prove an invitation can become the correct membership.
  • Release checks: verify deployed configuration, critical journeys, and agreed performance and security requirements.

These scopes overlap. An API acceptance test using a real database also tests that integration. Name what runs and what is substituted; labels alone tell the agent too little.

I use the same question to choose each check: what plausible failure would this catch? A database mock cannot prove a database constraint works. A success toast cannot prove the recipient received the right permissions.

Give the Agent a Brief

“Add comprehensive tests” leaves too much open. Start with this, alongside the feature specification:

Read the spec and existing test conventions.
Before editing, map each required behavior to:
- a concrete allowed or denied scenario;
- the public entry point or rule being tested;
- real dependencies and substitutes;
- expected results and forbidden side effects.

Include an admin from another workspace.
Flag missing requirements instead of inventing them.
Run relevant existing checks to establish a baseline.
Use isolated test data and controlled delivery.

Implement the agreed tests. For a regression, confirm
failure against the bug and success after the fix.
Do not weaken assertions or skip failures to get green.
After the final edit, rerun the required checks.
Report commands, results, skips, and unverified behavior.

Review What the Tests Prove

I review the tests against the requirement, not just the code. Could the route skip authorization and still pass? Could it return an error after saving the invitation? Ask the agent those questions before accepting its result.

A separate reviewer can help, but another agent can inherit the same assumption. Give it the original criteria and ask for a wrong implementation the tests would allow.

Keep verification proportional. A copy edit needs a preview and working links. A permission change needs evidence at the authorization boundary. Neither needs an arbitrary test count.

A passing report must identify the final code state and checks that actually ran. Crashed runners, zero discovered tests, and skipped suites are gaps. Repeated failures should produce a diagnosis, not an endless repair loop.
