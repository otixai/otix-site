Beyond Vibe Coding: A Step-by-Step First Project with Hypervelocity Engineering

How we used Microsoft's HVE Core and the RPI workflow to build a dock appointment scheduler — and why the constraint is the whole point.

AI Workflows Spec-Driven Methodology

If you've spent any time with AI coding assistants, you know the pattern. You ask Copilot to "add a booking endpoint," and it produces something that compiles, looks plausible, and quietly violates three conventions your team has held for years. The code isn't wrong, exactly. It's just not yours. Results vary by who's prompting, reviews get harder, and "it worked in my chat" becomes the new "it worked on my machine."

Microsoft's answer to this is Hypervelocity Engineering (HVE) — a methodology and open-source tooling framework (hve-core) that came out of their ISE team, the group that's been shipping AI solutions for enterprise clients at a pace that forced them to figure out what actually works. At Trility, we'd been running equivalent patterns on client engagements for over a year before Microsoft gave the approach a name, so when hve-core landed publicly, we were curious how our field-tested habits mapped onto their formalization.

The answer: closely. And the core idea is worth internalizing even if you never install the tooling.

The one-sentence version of HVE

Don't ask AI to write code. Ask it to research first, plan second, implement third, and review last — and make each phase produce an artifact the next phase consumes.

That's the RPI workflow (Research → Plan → Implement → Review), and the insight behind it is captured in a line from the HVE docs that we quote in nearly every conversation about this: when AI knows it cannot implement, it stops optimizing for "plausible code" and starts optimizing for "verified truth."

An AI agent that's allowed to write code will always drift toward writing code — investigation and implementation blur together. Constrain the agent to research-only, and suddenly it reads your codebase like an auditor instead of guessing like an intern with a deadline.

What we're building

To walk through the workflow, we need a project with enough real complexity that research actually matters. A to-do app won't cut it — there's nothing to discover. So we picked something from our own backyard: a Dock Appointment Scheduler.

If you've worked anywhere near logistics, you know the problem. A distribution center has a fixed number of dock doors. Carriers need to book time slots for pickups and deliveries. The scheduling rules are where it gets interesting:

  • No double-booking — one appointment per door per time slot
  • Turn buffers — 30 minutes between appointments on the same door for trailer swap
  • Carrier windows — some carriers can only book within contracted hours
  • Load-type constraints — refrigerated loads can only use doors with reefer hookups
  • Cancellation rules — appointments can be cancelled up to 2 hours before the slot

The stack: .NET 8 Web API, EF Core with SQL Server, and a minimal Razor Pages front end for the scheduling grid. Medium complexity, familiar tools, and — critically — enough business rules that an AI agent freestyle-coding it would absolutely get something wrong.

Step 0: Install HVE Core

The fastest path is the VS Code extension. Search the marketplace for HVE Core (publisher: ise-hve-essentials) and install it. That's genuinely it — the extension packages all the agents, prompts, and instruction sets, and they become available in Copilot Chat immediately. No configuration required.

If you live in the terminal, there's also a Copilot CLI plugin path:

copilot plugin marketplace add microsoft/hve-core
copilot plugin install hve-core@hve-core

Two things to know before you start:

  1. HVE agents create their working artifacts in a .copilot-tracking/ folder in your project. This is where research findings, plans, and phase state live. These artifacts are the connective tissue of the whole workflow — don't gitignore them reflexively; on our teams, we commit them alongside the code they produced.
  2. The /clear command is not optional hygiene — it's part of the methodology. You reset Copilot's context between phases. The artifacts carry the verified context forward; the chat history doesn't need to. More on why below.

Step 0.5: Onboard your AI like a new hire

Before you run a single RPI phase, do what Michael Brown (a Microsoft veteran who presented on HVE at Dallas Software Developers) frames as onboarding: treat the AI like an eager junior developer joining your team. High velocity, genuine enthusiasm, zero domain context, and no sense of where the boundaries are — until you supply them.

For a human junior dev, you'd hand over coding standards, point at a well-built example feature, and explain the domain. Do exactly that for the AI, in a copilot-instructions.md file at the root of your repo:

  • Coding standards and conventions — the ones your team actually enforces, not aspirational ones
  • An example vertical slice — point at your cleanest existing feature ("appointments should follow the pattern in src/DockScheduler/Facilities/") so the AI has a house-style reference
  • Explicitly disallowed patterns and libraries — "do not add caching layers, do not introduce MediatR, do not use DateTime.Now" is worth more than a page of positive guidance
  • Domain context — a paragraph on what the business actually does

That last one matters more than it looks. Brown's example: the same feature request means very different architecture for an e-commerce platform than for a physical farm-supply operation. In our world, "book an appointment" means something very specific when the resource is a dock door with a reefer hookup and the customer is a carrier with contracted hours. Two sentences of domain context in the instructions file prevent an entire category of wrong architectural assumptions.

And treat these files as what they are: version-controlled code assets. They get reviewed in PRs, they evolve as the team learns, and they're arguably the highest-leverage code in the repository — every generated line downstream inherits their quality.

Step 1: Research (/rpi-research)

Open Copilot Chat (Ctrl+Alt+I), type /rpi-research, and describe what you need investigated — not what you want built. The framing matters. Here's roughly what we used:

Research what's needed to add appointment booking to this solution.

Consider:
* Existing entity and DbContext patterns in src/DockScheduler.Data
* How validation is currently handled (FluentValidation? data annotations?)
* Existing API conventions: routing, response envelopes, ProblemDetails usage
* How time zones are handled — appointments are local to the facility
* Concurrency: what happens when two carriers book the same slot simultaneously?
* Existing test patterns in tests/ (xUnit? fixtures? test data builders?)

Notice what's in that prompt: questions, not requirements. The research agent's job is to read the codebase and come back with verified findings — which patterns exist, which conventions are in force, where the landmines are.

For our scheduler, the research phase surfaced things we would have hand-waved past:

  • The existing DbContext used a rowversion-based optimistic concurrency pattern on other entities — so the double-booking rule shouldn't be a "check then insert" (race condition), it should lean on a unique constraint plus concurrency token.
  • Time handling in the codebase was inconsistent (some DateTime, some DateTimeOffset) — the research flagged this as a decision the plan needed to make explicitly, not inherit accidentally.
  • The API used ProblemDetails for errors everywhere except one legacy controller — so new endpoints should follow the majority pattern.

This is the payoff. None of that is exotic, but every one of those is exactly the kind of thing a freestyle AI session gets wrong — and gets wrong invisibly, in code that compiles and demos fine.

The findings land as a durable artifact in .copilot-tracking/. Read it. Correct it if it's wrong. This is your first human gate.

Step 2: Plan (/rpi-plan)

Now type /clear to reset the context, then /rpi-plan. Feed it the requirements informed by the research findings:

Create an implementation plan for appointment booking.

Requirements from research:
* New Appointment entity following existing entity conventions, with
  rowversion concurrency token
* Unique index on (DockDoorId, SlotStart) to enforce no double-booking
  at the database level
* All times stored as DateTimeOffset; facility time zone applied at the
  API boundary
* Booking rules as a domain service: 30-min turn buffer, carrier window
  check, reefer-door compatibility
* Endpoints follow existing routing + ProblemDetails conventions
* xUnit tests using the existing test data builder pattern

Why the /clear between phases? Context pollution is real. A long chat session accumulates half-formed ideas, abandoned directions, and the model's own earlier speculation — and all of it influences what comes next. RPI's answer is that phases hand off through artifacts, not chat history. The plan phase starts fresh, reads the research findings, and produces a plan. Clean inputs, clean outputs.

The plan that comes back is a structured, step-by-step specification: which files to create, what goes in each, and validation criteria for knowing when each step is done. For our scheduler it broke into six steps — entity + migration, unique index, domain service with the booking rules, endpoints, validation, tests.

This is your second human gate, and it's the important one. Reviewing a plan is dramatically cheaper than reviewing generated code. A wrong assumption caught here costs you a sentence edit. The same assumption caught in a PR costs you a rewrite. Spend your senior-engineer attention here.

Step 3: Implement (/rpi-implement)

/clear again, then /rpi-implement, and hand it the approved plan. The implement agent works through the plan step by step, showing you each file change for approval as it goes.

What surprised people on our teams the first time: this phase is boring. That's the compliment. There's no watching the AI improvise architecture in real time, no "wait, why is it adding a Redis dependency?" moment. The creativity happened in research and planning, where it was cheap to redirect. Implementation is just execution against a spec — the agent even self-corrects against the plan's validation criteria as it completes each step.

For the scheduler, implementation produced the migration with the unique index, the BookingService with all five business rules, endpoints that matched the house ProblemDetails style, and tests using the existing builder pattern — because all of those decisions were already made, in writing, before a line of code existed.

Run your build and tests. dotnet build, dotnet test. Then hit the concurrency case manually or with a quick integration test: two simultaneous bookings for the same door and slot, one succeeds, one gets a clean 409. It does, because the research phase found the pattern and the plan committed to it.

Step 4: Review (/rpi-review)

The newest formalized phase, and the one teams skip at their peril. /clear, then /rpi-review. The review agent validates the implementation against the research findings and the plan — not against vibes. Did every plan step get completed? Do the artifacts and the code agree? Did implementation drift from a convention that research documented?

Think of it as a diff between "what we said we'd build" and "what got built," performed by an agent that has both documents. It caught one drift in ours: the implement phase had quietly used DateTime.UtcNow in a cancellation-window check instead of the injected clock abstraction the plan specified. Small, testable, exactly the kind of thing human reviewers gloss over at 4:45 on a Friday.

The shortcut, once you've earned it

Running the four phases manually with /clear between them is the right way to learn RPI — you see each phase's responsibility and artifact. For day-to-day work, HVE Core ships a coordinated RPI Agent: select it from the agent picker (or invoke /rpi) and describe the task once. It orchestrates the same phase skills, including Review, without the manual switching.

Same constraint system, same artifacts, less ceremony. But run the manual loop at least once. You'll trust the coordinated agent more when you know exactly what it's doing on your behalf.

What this actually changes

A few honest observations from doing this on real work, not just demos:

The code becomes disposable; the specs become the asset. Brown's framing is that AI-generated code is a sketch — if a plan yields poor code, don't patch the code, fix the plan and regenerate. That inverts what you protect. When implementation is cheap and reproducible from an approved plan, the durable assets are the research findings, the plan, and the instructions file — not the generated lines. That's why we commit .copilot-tracking/ artifacts: they're the source; the code is increasingly the build output.

The artifacts outlive the task. The research findings for our scheduler are now the best onboarding document that codebase has for its booking domain. Nobody set out to write documentation; it fell out of the workflow.

Your role shifts from author to reviewer — at the two points where review is cheap. Reading a research summary and approving a plan takes minutes. It's the highest-leverage minutes in the whole cycle. That shift is bigger than one workflow, and Brown says the quiet part out loud: pure line-by-line coding capacity is depreciating. What appreciates is exactly what RPI asks of you — domain expertise, architectural judgment, and the ability to specify precisely.

It's slower for trivial tasks, and that's fine. Nobody needs RPI to rename a variable. The methodology pays for itself when there are genuine unknowns — existing patterns to discover, conventions to honor, integration seams to respect. Our rule of thumb: if you'd assign the task to a new team member with a written brief, it's an RPI task.

Fair warning: Microsoft is explicit that hve-core is a highly opinionated, rapidly evolving framework — patterns to learn from, not a stable platform to build a production dependency on. Treat it that way. The tooling will change; the discipline underneath it won't.

Try it yourself

Pick something with real rules — your domain has one, we promise. Install the extension, write the instructions file, run /rpi-research on your own codebase with genuine questions, and read what comes back before you let anything write code.

And keep Microsoft's own rule for AI-assisted delivery taped to your monitor: AI code is still your code. If you can't explain it, understand it, maintain it, and support it, don't ship it. Everything in this post — the onboarding, the phases, the artifacts, the gates — exists to make that standard achievable at speed.

The velocity in Hypervelocity Engineering doesn't come from the AI typing fast. It comes from never having to throw away plausible-but-wrong code again.
