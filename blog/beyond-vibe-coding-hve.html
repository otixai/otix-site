Beyond Vibe Coding: Teaching Myself Hypervelocity Engineering

Working notes on Microsoft's HVE and the RPI workflow: how it maps onto the multi-agent research, plan, and implement loop I already run, and what happens when I point it at a people-search feature.

AI Workflows Spec-Driven Working Notes

Let me be upfront about what this is. I haven't shipped a feature with Microsoft's HVE tooling in anger. This post is how I teach myself a thing: I research it, I write the walkthrough as if I'm executing it, and by the time the draft is done I can actually speak to it. So treat this as learning notes, not a case study. The honest parts are the places where HVE lines up with a multi-agent loop I've already been running for real, and the places where I've already bruised myself on the exact problems it's trying to solve.

If you've spent any time with AI coding assistants, you know the pattern. You ask for "add a booking endpoint," and you get something that compiles, looks plausible, and quietly violates three conventions your team has held for years. The code isn't wrong, exactly. It's just not yours. Results vary by who's prompting, reviews get harder, and "it worked in my chat" becomes the new "it worked on my machine."

Microsoft's answer is Hypervelocity Engineering (HVE), a methodology and open-source tooling framework (hve-core) that came out of Microsoft engineers shipping AI solutions under real delivery pressure and needing to figure out what actually holds up. What caught my attention wasn't the tooling. It's that the methodology is almost exactly the loop I'd already cobbled together by trial and error, just with names, artifacts, and guardrails I never bothered to formalize.

The One-Sentence Version of HVE

Don't ask AI to write code. Ask it to research first, plan second, implement third, and review last, and make each phase produce an artifact the next phase consumes.

That's the RPI workflow (Research, Plan, Implement, Review), and the insight behind it is captured in a line from the HVE docs: when AI knows it cannot implement, it stops optimizing for "plausible code" and starts optimizing for "verified truth." (The current docs actually formalize a fifth concept, Follow-up, for routing whatever the review turns up; this walkthrough sticks to the core four.)

An AI agent allowed to write code will always drift toward writing code; investigation and implementation blur together. Constrain the agent to research-only, and suddenly it reads your codebase like an auditor instead of guessing like an intern with a deadline. That single sentence is the one I most wish I'd internalized a year ago.

What I've Already Been Doing (and Didn't Have a Name For)

Here's the experience I'm reading HVE against. I recently did a greenfield rewrite of a roughly decade-old assignment-and-scheduling system (the kind of thing that had accreted years of edge cases) and delivered it in a few months. I did almost none of it by hand-typing code into a single chat. I ran it as a multi-agent pipeline across OMC (oh-my-claudecode), OMP, and Claude, with different agents owning different jobs.

The loop looked like this, and I stumbled into it rather than designing it:

  • Build a context wiki first. The old system's knowledge lived in Confluence: scattered, contradictory, and half-stale. I had agents mine Confluence and distill it into a local set of context wikis with the domain rules, the vocabulary, and the "why is it like this" decisions. That wiki, not the chat, became the substrate everything downstream read from.
  • Turn research into stories. From that verified context I wrote stories: small, scoped units of work with the domain rules attached, so no downstream agent had to rediscover them.
  • Turn stories into plans, then implementations, with different agents. One agent planned. A different agent implemented. Keeping those roles on separate agents (and separate contexts) mattered more than I expected: the planner didn't get to quietly start coding, and the implementer inherited a spec instead of a vibe.

Nobody handed me RPI. I arrived at "research becomes an artifact, the artifact feeds a plan, the plan feeds implementation, and you keep the roles apart" because the alternatives kept burning me. Reading the HVE docs was less "here's a new idea" and more "oh, that's the name for the thing I've been doing badly on purpose."

How My Habits Map onto HVE

The mapping is close enough that it's worth spelling out, because the gaps are where HVE taught me something:

  • My Confluence-mined context wiki is HVE's research artifact. Same idea: a durable, human-checkable record of verified findings that the next phase reads instead of trusting chat memory. HVE just gives it a home (.copilot-tracking/) and a phase (/rpi-research) instead of me improvising the format.
  • My stories and plans are the HVE Plan phase. I was already writing scoped specs before implementation. HVE formalizes the plan as the artifact you review, and insists the review happen before code, which I only did about half the time.
  • My different-agent-per-role trick is HVE's phase skills plus /clear. This is the one that clicked hardest. I was using separate agents to keep the planner from coding; HVE gets the same isolation with one tool by resetting context between phases and handing off through artifacts. Same discipline, less machinery.
  • The standards I kept re-pasting are copilot-instructions.md. I was forever re-stuffing conventions into system prompts and wiki headers. HVE's instruction file is just that, version-controlled, in one place.
  • The drift-check I did by hand is the Review phase. I used to eyeball whether the implementation matched the story. HVE makes it a phase (/rpi-review) with both documents in hand. More on why that's the phase I most underrated.

The Rabbit Holes (Learned the Hard Way)

The reason I believe HVE's constraints are load-bearing is that I've fallen into every hole they're built to prevent:

  • Research that never converges. Give an eager agent an open-ended "go understand this," and it will happily generate context wikis forever. Left ungated, mine sprawled into pages nobody would read. HVE's answer is a forcing function I didn't impose on myself early enough: research produces one artifact you actually inspect and correct.
  • Context bloat. My worst sessions were the ones where I dragged a giant chat forward into the next task: half-formed ideas, abandoned directions, the model's own earlier speculation. It poisons everything downstream. The habit of clearing context between phases isn't hygiene theater; it's the fix for the exact failure that cost me the most time.
  • Handoff drift. Even with separate planner and implementer agents, the implementer would silently diverge from the plan: a swapped abstraction here, an inlined shortcut there, and I wouldn't notice until much later. That's precisely what a real Review phase catches, and precisely what I kept skipping.
  • Wiki rot. A context wiki mined from Confluence is a snapshot. When the source moved and the wiki didn't, agents confidently built on stale truth. HVE's artifacts are ephemeral by design, scoped to a task and dated, which is the opposite failure mode but the same lesson: a document that outlives the moment it was true for is a liability unless someone owns keeping it honest.

So when the HVE docs sound opinionated to the point of fussy, my honest reaction is: yes, and every one of those opinions maps to a specific way I've wasted a week.

Step 0: Install HVE Core

The fastest path is the VS Code extension. Search the marketplace for HVE Core (publisher: ise-hve-essentials) and install it. That's it: the extension packages all the agents, prompts, and instruction sets, and they become available in Copilot Chat immediately. No configuration required.

If you live in the terminal, there's also a Copilot CLI plugin path:

copilot plugin marketplace add microsoft/hve-core
copilot plugin install hve-core@hve-core

Two things to know before you start:

  1. HVE agents create their working artifacts in a .copilot-tracking/ folder in your project. This is where research findings, plans, and PR-review notes live. Microsoft's install guide tells you to add .copilot-tracking/ to .gitignore, treating the artifacts as ephemeral scratch space rather than committed history. (My own instinct from the multi-agent work is to keep at least the research and plan artifacts somewhere durable, because they turned out to be the best onboarding docs I had. But that's a deviation from the default, so decide it deliberately rather than by accident.)
  2. The /clear command is a context-management tool, not a mandatory ritual. The docs are explicit that a reset is "a tool for clarity, not a requirement." Use it when a long lifecycle has accumulated cruft or you're switching phases. The artifacts, not the chat history, are what carry verified context forward; that's why clearing is safe. In my own multi-agent work I learned to reset context far more often than felt natural, which is the same instinct with a command name.

Step 0.5: Onboard Your AI Like a New Hire

Before you run a single RPI phase, I onboard the AI the way I'd onboard an eager junior developer joining the team: high velocity, genuine enthusiasm, zero domain context, and no sense of where the boundaries are until you supply them. This matches my experience precisely: the agent's velocity is never the problem; its missing context is.

For a human junior dev, you'd hand over coding standards, point at a well-built example feature, and explain the domain. Do exactly that for the AI, in a copilot-instructions.md file at the root of your repo. It's the standard GitHub Copilot custom-instructions mechanism, which HVE's agents read like everything else in the workspace:

  • Coding standards and conventions: the ones your team actually enforces, not aspirational ones
  • An example vertical slice: point at your cleanest existing feature so the AI has a house-style reference
  • Explicitly disallowed patterns and libraries: "do not add caching layers, do not introduce MediatR, do not use DateTime.Now" is worth more than a page of positive guidance
  • Domain context: a paragraph on what the business actually does

That last one matters more than it looks. The same feature request means very different architecture for an e-commerce platform than for a physical operation with real-world constraints. In the example below, "find a person" turns out to mean "who's free, where can they travel, and what are they trained to do," which is nothing like a name lookup. Two sentences of domain context in the instructions file prevent an entire category of wrong architectural assumptions. I've paid for that category more than once.

And treat these files as what they are: version-controlled code assets. They get reviewed in PRs, they evolve as the team learns, and they're arguably the highest-leverage code in the repository, because every generated line downstream inherits their quality.

What I'm Building: People Search

To walk the workflow, I need a feature with enough real rules that research actually matters. A rename won't teach me anything. So the example here is adding people search to an event-planning app: an organizer needs to find the right people to staff and speak at events. Think less "look up a name" and more "who's available for a conference in the Atlanta area next spring, and has the training this session needs."

It sounds trivial until you write down what "the right people" means, and it's exactly the kind of feature where an unstructured session gets something wrong invisibly:

  • Availability: results have to respect when each person is actually free; someone booked solid that week should never come back as a match
  • Location and travel: "the Atlanta area" is a geography question, not a string match; you need a region or radius, not people whose bio happens to mention Atlanta
  • Skills and training: people carry structured skills, certifications, and training, and matching those well is the whole point of the feature
  • Matching and scale: you're ranking across availability, geography, and skills at once, and a naive LIKE '%term%' scan falls over on a large people table, so this wants a real full-text or search index
  • Scoping and paging: results are scoped to the organization's own people and events, and paged to match the app's existing paging envelope

The stack, purely to make the example concrete: .NET 8 Web API, EF Core with SQL Server, and a minimal Razor Pages results grid. Medium complexity, familiar tools, and enough rules that an agent improvising it would happily return people who aren't actually free that week, or fall back to an unindexed scan that crawls on a real people table.

Step 1: Research (/rpi-research)

Open Copilot Chat (Ctrl+Alt+I), invoke /rpi-research, and describe what you need investigated, not what you want built. The framing matters. Here's roughly what I'd use:

Research what's needed to add people search to this solution.

Consider:
* Existing entity and DbContext patterns for people/attendees
* How availability is modeled and computed today (a scheduling
  service? a query? denormalized flags?)
* How location/region is stored, and whether there's existing geo
  or region matching to reuse
* How skills, certifications, and training are modeled and queried
* Existing search/filter patterns: LINQ LIKE, raw SQL, or a
  full-text index
* Existing API conventions: routing, the paging response envelope,
  ProblemDetails usage
* Existing test patterns in tests/ (xUnit? fixtures? data builders?)

Notice what's in that prompt: questions, not requirements. The research agent's job is read-only. It searches the codebase and relevant sources and comes back with cited findings, distinguishing evidence from assumption. This is the phase my Confluence-mining habit maps straight onto. Worth knowing: HVE treats research as conditional. If you already have adequate, verified evidence, you're meant to reuse it and skip straight to planning rather than re-investigating out of habit.

For people search, the Research phase would surface things I'd otherwise hand-wave past:

  • Availability is already computed by an existing scheduling service, so people search has to call that rather than reimplement "is this person free" and drift out of sync with the real calendar.
  • Location matching already exists for venues as a region lookup, so the same approach should apply to people instead of a bespoke string match on a city field.
  • The app has an established paging envelope and uses ProblemDetails for errors everywhere except one legacy controller, so the new endpoint should follow the majority pattern.

None of that is exotic, but every one of those is exactly the kind of thing an unstructured session gets wrong, and gets wrong in code that compiles and demos fine. The findings land as a durable, cited artifact under .copilot-tracking/research/. Read it. Correct it if it's wrong. This is your first human gate.

Step 2: Plan (/rpi-plan)

Reset the context if the research thread has gotten long (/clear or a fresh chat), then invoke /rpi-plan. Feed it the requirements informed by the research findings:

Create an implementation plan for people search.

Requirements from research:
* New search endpoint following existing routing, paging envelope,
  and ProblemDetails conventions
* Call the existing scheduling service for availability instead of
  reimplementing it, so results never claim someone is free when
  the calendar says otherwise
* Reuse the existing region lookup for "near a location" matching
* Match on skills, certifications, and training
* Full-text index across name, skills, and location so search does
  not fall back to a table scan
* Results scoped to the caller's organization and its events
* Paged results using the existing paging envelope
* xUnit tests using the existing test data builder pattern, including
  a test that a person who is not available in the window never appears

Why reset context between phases? Context pollution is real, and it's the failure that has cost me the most. A long chat accumulates half-formed ideas, abandoned directions, and the model's own earlier speculation, and all of it influences what comes next. RPI's answer is that phases hand off through dated artifacts, not chat history. The Plan phase reads the research findings and produces a plan. Clean inputs, clean outputs.

What comes back is more than one file. HVE's Plan phase produces a sequenced plan with stable phase and task IDs, a phase-details document, and the part I didn't have in my hand-rolled version: an independent critique that has to record Pass, Revise, or Blocked before implementation is considered ready. So there's an automated review of the plan, and then your own.

That's your second human gate, and it's the important one. Reviewing a plan is dramatically cheaper than reviewing generated code. A wrong assumption caught here costs you a sentence edit. The same assumption caught in a PR costs you a rewrite. Spend your senior-engineer attention here; this is the gate I used to skip, and skipping it is what handoff drift feeds on.

Step 3: Implement (/rpi-implement)

Reset again if needed, invoke /rpi-implement, and hand it the approved plan and phase details. The implement agent works through the plan step by step, recording each material change and its validation as it goes.

What surprises people the first time: this phase is boring. That's the compliment. There's no watching the AI improvise architecture in real time, no "wait, why is it adding a Redis dependency?" moment. The creativity happened in research and planning, where it was cheap to redirect. Implementation is just execution against a spec, and if it needs to depart from the plan, HVE makes it record the divergence and send the amendment back for a fresh critique rather than quietly winging it.

For people search, implementation would produce the full-text index, a PeopleSearchService that calls the scheduling service for availability and the existing region lookup for location, an endpoint matching the house paging envelope and ProblemDetails style, and tests using the existing builder pattern, because all of those decisions were already made, in writing, before a line of code existed.

Run your build and tests. dotnet build, dotnet test. Then hit the case that actually matters manually or with a quick integration test: search for people available for an event in Atlanta on specific dates, and confirm that someone whose calendar is full those days never shows up, no matter how well they match on skills. They shouldn't, because the Research phase found the scheduling service and the plan committed to calling it.

Step 4: Review (/rpi-review)

The acceptance phase, and (going by my own track record) the one teams skip at their peril. Reset context, then invoke /rpi-review. The review agent validates the implementation against the research findings and the plan, not against vibes. Did every plan task get completed? Do the artifacts and the code agree? Did implementation drift from a convention that research documented? It records findings with severity grades. It also keeps execution status (Complete, Partial, Blocked) separate from outcome (Conformant, Defects found, and so on), so "the code got written" never gets mistaken for "the work got accepted."

Think of it as a diff between "what we said we'd build" and "what got built," performed by an agent that has both documents. The drift I'd most expect it to catch in people search is the quiet one: the Implement phase deciding it's simpler to read an IsAvailable flag off the person record instead of calling the scheduling service the plan specified. It compiles. It demos fine. And it books people who aren't actually free, because that flag went stale the moment someone's calendar changed. That's the same shape as the handoff drift that used to bite me, which is why I don't treat Review as optional.

The Shortcut, Once You've Earned It

Running the phases manually is the right way to learn RPI; you see each phase's responsibility and artifact. For day-to-day work, HVE Core ships coordinated entry points: select the RPI Agent from the agent picker, or use /rpi-quick (or /rpi) to drive the whole lifecycle from a single prompt. Same constraint system, same artifacts, less manual switching, which is essentially the multi-agent pipeline I hand-wired, packaged. The docs are careful to note these are lifecycle wrappers, not autonomous dispatchers that go off and build things unattended.

But run the manual loop at least once. You'll trust the coordinated agent more when you know exactly what it's doing on your behalf.

What This Actually Changes

A few observations, some from HVE's docs and how its practitioners talk about it, some from my own multi-agent scars:

The code becomes disposable; the specs become the asset. The framing I keep hearing is that AI-generated code is a sketch: if a plan yields poor code, don't patch the code, fix the plan and regenerate. That inverts what you protect, and it's the same instinct that made me treat my context wikis as the real deliverable. When implementation is cheap and reproducible from an approved plan, the durable assets are the research findings, the plan, and the instructions file, not the generated lines.

The artifacts carry the context. On my rewrite, the research and plan documents were what let a different agent pick up the next phase without re-learning the domain. HVE's .copilot-tracking/ artifacts are the same idea with a filing system: dated, task-scoped, and explicitly the thing that survives a context reset.

Your role shifts from author to reviewer, at the two points where review is cheap. Reading a research summary and approving a plan takes minutes, and those minutes buy you the most in the whole cycle. The uncomfortable version of this: pure line-by-line coding capacity is depreciating. What appreciates is exactly what RPI asks of you: domain expertise, architectural judgment, and the ability to specify precisely.

It's slower for trivial tasks, and that's fine. Nobody needs the full lifecycle to rename a variable, and HVE itself tells you to pick the smallest action that fits and skip research when your evidence is already adequate. The methodology pays for itself when there are genuine unknowns: existing patterns to discover, conventions to honor, integration seams to respect. My rule of thumb: if you'd assign the task to a new team member with a written brief, it's an RPI task.

Fair warning: hve-core's development tip is a fast-moving, opinionated framework. The docs distinguish the ref-less main from reviewed Stable and PreRelease channels precisely because the tip doesn't carry published-release assurance. Treat it as patterns to learn from, and pin a channel if you depend on it. The tooling will change; the discipline underneath it, the same discipline I arrived at the hard way, won't.

Try It Yourself

Pick something with real rules; your domain has one, I promise. Install the extension, write the instructions file, run /rpi-research on your own codebase with genuine questions, and read what comes back before you let anything write code.

And keep the one rule that makes all of this safe taped to your monitor: AI code is still your code. If you can't explain it, understand it, maintain it, and support it, don't ship it. All of it, the onboarding, the phases, the artifacts, the gates, exists to make that standard achievable at speed.

The velocity in Hypervelocity Engineering doesn't come from the AI typing fast. It comes from never having to throw away plausible-but-wrong code again, which, having thrown away plenty, is the promise I most want to hold it to.

These are working notes, written to teach myself HVE by mapping it onto a multi-agent loop I already run, and to have something to come back to. I haven't shipped a production feature with the HVE tooling itself yet; the honest claims here are about the underlying discipline, not the extension. If it holds up when I actually point it at real work, that will be worth a follow-up.
