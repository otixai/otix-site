Three Local AI Agents Walk Into a Legacy Codebase

Building an adversarial refactoring loop with pi, Ollama, and zero API costs on an M4 MacBook Air.

Local Models Multi-Agent Refactoring

Most coding agent demos show one model talking to itself. Write code, run tests, fix code, ship it. That's fine for greenfield work. But legacy code is adversarial by nature — the original developer is fighting you from the grave, and your assumptions about what the code does are wrong until proven otherwise.

So we built a loop where four agents argue about the Gilded Rose refactoring kata. One writes tests to pin behavior. One verifies the test results. One refactors to make the failing tests pass. A reviewer checks the final result. All running locally on an M4 MacBook Air through Ollama, orchestrated by pi — Mario Zechner's minimal terminal coding agent.

No API keys. No cloud. No token bills. Just a local model arguing with itself through the filesystem until the tests pass.

Why Pi

Pi doesn't have built-in sub-agents, plan mode, or any of the scaffolding that other coding agents bake in. That's the point. It gives the model four tools — read, write, edit, bash — and gets out of the way.

The sub-agent pattern in pi is just shell composition: pi -p "your prompt" spawns a headless instance that does its work and exits. Your orchestrator is a bash script. Your agent definitions are short markdown files. There's no framework to learn, no YAML to configure, no abstraction layer between you and what's actually happening.

Pi also supports Ollama natively as a provider, so pointing it at local models is a config file and nothing else.

The Hardware

M4 MacBook Air, top spec — 32GB unified memory. That's the constraint we're designing around. Ollama keeps the model loaded in memory between calls, so once it's warm there's no swap penalty between agent turns. The budget is roughly: any single model up to ~24GB, with headroom for the OS and KV cache.

The Model

One model for all four agents: qwen3-coder:30b (19GB, MoE 30B/3.3B active).

This is a Mixture-of-Experts model — 30 billion total parameters, but only 3.3 billion activate per token. A router network selects which "experts" fire on each pass, giving you broad code knowledge with fast inference. More importantly, this model was trained on 7.5 trillion tokens at a 70% code ratio with execution-driven reinforcement learning. It didn't just read code — it learned by running code and observing what happened. That RL training is exactly what you want for an agent loop that's edit-test-fix on repeat.

We tried GLM-4.7-Flash (dense 30B) first. It wrote excellent tests but couldn't close the implementation loop — it would analyze the failures, explain what needed to change, and then not actually change it. Dense models put all 30B parameters behind every token, which is great for deep reasoning but doesn't translate into "use the edit tool to fix line 27." The Qwen3 Coder's RL training on execution loops makes it meaningfully better at the agentic part — calling tools, reading output, calling tools again.

One model, loads once, stays hot. Zero swap overhead. The adversarial tension comes from the prompt constraints, not model diversity — each agent gets a fresh context window and a narrow mandate.

ollama pull qwen3-coder:30b

What We'd Run With More RAM

For the curious: qwen3-coder-next is the model we actually wanted. It's an 80B MoE with only 3B active parameters per token, trained on 800K executable tasks with environment interaction and RL. It performs roughly on par with Claude Sonnet 4.5 on SWE-Bench Pro — absurd for an open-weight model. But the Q4 quant is 52GB. If you're reading this on a 64GB Mac, pull it. You'll know immediately why we wanted it.

Setting Up Pi with Ollama

Install pi:

npm install -g @mariozechner/pi-coding-agent

Create ~/.pi/agent/models.json:

{
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "compat": {
        "supportsDeveloperRole": false,
        "supportsReasoningEffort": false
      },
      "models": [
        { "id": "qwen3-coder:30b", "name": "Qwen3 Coder 30B MoE", "reasoning": true }
      ]
    }
  }
}

The compat block matters. Ollama doesn't support the developer message role or reasoning_effort parameter that pi uses for some cloud providers. This tells pi to fall back to standard system messages. Without it, you'll get silent failures.

Create ~/.pi/agent/settings.json:

{
  "defaultProvider": "ollama",
  "defaultModel": "qwen3-coder:30b"
}

Verify it works:

pi -p "Say hello and list your available tools."

If you see it call bash or read successfully, you're wired up.

The Kata

The Gilded Rose is a refactoring classic. You inherit a gnarly updateQuality() method full of nested conditionals. You can't touch the Item class. Your job is to refactor it into something sane and add support for "Conjured" items that degrade twice as fast.

It's a perfect adversarial target because the original code is deliberately opaque, the requirements have edge cases that are easy to miss, and you can verify correctness mechanically — the tests either pass or they don't.

git clone https://github.com/emilybache/GildedRose-Refactoring-Kata.git
cd GildedRose-Refactoring-Kata/js-jest
npm install

Any language works. We're using the JavaScript/Jest version here because there's no compile step, the test runner gives clean parseable output, and local models handle vanilla JS more reliably than TypeScript — one fewer abstraction layer for a 3.3B-active model to get wrong.

The Agent Definitions

This is where most of the engineering happened. Getting a local model to act as a coding agent instead of a helpful assistant requires very specific prompt construction. Every lesson here came from watching the loop fail live.

Lesson 1: Say "use your tools" first

Local models default to assistant mode. They'll write a perfect explanation of what needs to change, wrap it in a markdown code block, and never touch the filesystem. The first line of every agent prompt has to break this pattern: "You are a coding agent. Use your tools to read and write files directly. Do not explain code. Do not show examples. Edit files on disk."

Lesson 2: Name the tools explicitly

Pi gives the model read, write, edit, and bash. Mentioning these by name in the numbered steps primes the model to emit tool calls instead of prose. "Use read to open src/gilded_rose.js" is better than "Read the source file."

Lesson 3: Read existing files before writing

The js-jest kata uses CommonJS (require). If the model doesn't read the existing test file first, it'll write ES module syntax (import { Item } from './Item') and Jest will crash before any test runs. The fix: step 1 of the test writer is always "read the existing test file and match its patterns."

Lesson 4: Add a verifier agent

Raw Jest output is noisy — stack traces, ANSI codes, timing info, file paths. Asking a 3.3B-active model to parse that noise AND figure out what to fix is two hard jobs in one prompt. A dedicated verifier agent runs the tests and produces a clean structured summary. The implementer gets "test X: expected 3, got 5" instead of a wall of terminal output.

Here are all four agent definitions. These go in .pi/agents/ at the project root.

.pi/agents/test-writer.md:

You are a coding agent. Use your tools to read and write files directly.
Do not explain code. Do not show examples. Edit files on disk.
1. Use read to open test/gilded_rose.test.js. Note the require style.
2. Use read to open src/gilded_rose.js. Understand every branch.
3. Use write or edit to add tests to test/gilded_rose.test.js.
   Match the existing require/import style exactly.
4. Cover: normal items, Aged Brie, Sulfuras, Backstage passes.
5. Cover edges: quality 0, quality 50, sellIn 0, negative sellIn.
6. Add FAILING tests for "Conjured" items that degrade 2x as fast.
7. Only modify files in test/. Never touch src/.
8. Use bash to run `npm test`. Read the output to confirm tests run.

.pi/agents/verifier.md:

You are a coding agent. Do not modify any files.
1. Use bash to run `npm test`.
2. Read the full output including any errors before the test summary.
3. If tests crashed (syntax errors, import errors), report the exact error.
4. If tests ran, report: X passed, Y failed, and each failure name.
5. If all passed, say: ALL PASS

.pi/agents/implementer.md:

You are a coding agent. Use your tools to read and edit files directly.
Do not explain code. Do not show examples. Edit files on disk.
1. Use read to open src/gilded_rose.js.
2. Read the failing test summary below.
3. Use edit to modify src/gilded_rose.js to fix each failure.
4. Do NOT touch the Item class. Do NOT modify any test files.
5. Use bash to run `npm test` after each edit.
6. Read the output. If tests fail, edit again. Repeat until green.

.pi/agents/reviewer.md:

You are a coding agent. Do not modify any files.
1. Use read to open src/gilded_rose.js.
2. Use read to open every file in test/.
3. Use bash to run `npm test`. Confirm all tests pass.
4. Check: all Gilded Rose requirements covered including Conjured.
5. Check: Item class is unmodified.
6. Check: code is readable and extensible.
7. Report: PASS or FAIL with specific issues.

These are tight by design. Local models have smaller effective context windows than cloud models, and every token of system prompt is a token not spent on reasoning. Say what the agent is, what tools to use, what files to touch, and how to verify. Nothing else.

The Orchestrator

This is the loop. A bash script that cycles through test writing, verification, implementation, and verification again, with up to three rounds before the reviewer passes judgment.

run-kata.sh:

#!/usr/bin/env bash
set -euo pipefail

DIR="$(cd "$(dirname "$0")" && pwd)"
cd "$DIR"

MODEL="qwen3-coder:30b"
MAX_ROUNDS=3
ROUND=1

run_agent() {
  local label="$1"
  local prompt="$2"
  local logfile="$3"
  echo "$label"
  pi -p "$prompt" --provider ollama --model "$MODEL" 2>&1 | tee "$logfile"
}

verify() {
  local logfile="$1"
  run_agent "🔍 Verifier..." "$(cat .pi/agents/verifier.md)" "$logfile"
}

echo "=== GILDED ROSE ADVERSARIAL KATA ==="
echo "Model: $MODEL"
echo ""

while [ $ROUND -le $MAX_ROUNDS ]; do
  echo "══════ ROUND $ROUND/$MAX_ROUNDS ══════"

  # --- Test Writer ---
  TW_PROMPT=$(cat .pi/agents/test-writer.md)
  if [ $ROUND -gt 1 ]; then
    TW_PROMPT="$TW_PROMPT

Round $ROUND: tests already exist. Read current tests first.
Only add tests for coverage gaps. Do not rewrite existing tests."
  fi
  run_agent "🧪 Test Writer..." "$TW_PROMPT" "/tmp/kata-r${ROUND}-tests.log"

  # --- Verify after test writing ---
  verify "/tmp/kata-r${ROUND}-verify-tests.log"

  # --- Implementer gets structured failure summary ---
  VERIFY_OUTPUT=$(cat "/tmp/kata-r${ROUND}-verify-tests.log" | tail -30)

  IMPL_PROMPT="$(cat .pi/agents/implementer.md)

Current test results from verifier:
\`\`\`
$VERIFY_OUTPUT
\`\`\`"
  run_agent "🔧 Implementer..." "$IMPL_PROMPT" "/tmp/kata-r${ROUND}-impl.log"

  # --- Verify after implementation ---
  verify "/tmp/kata-r${ROUND}-verify-impl.log"

  # --- Check if we're green ---
  RESULT=$(npm test 2>&1 || true)
  if echo "$RESULT" | grep -q "Tests:.*passed" && ! echo "$RESULT" | grep -q "failed"; then
    echo "✅ All tests passing after round $ROUND"
    break
  else
    echo "$RESULT" | tail -5
    echo "❌ Still failing, continuing..."
  fi

  echo ""
  ROUND=$((ROUND + 1))
done

# --- Reviewer ---
echo ""
run_agent "📋 Reviewer..." "$(cat .pi/agents/reviewer.md)" "/tmp/kata-review.log"

echo ""
echo "=== DONE. Logs in /tmp/kata-*.log ==="
chmod +x run-kata.sh

Run it with ./run-kata.sh. Sit back. Watch the agents fight.

What's Actually Happening

Round 1: The test writer uses read to open the existing test file, sees the require() pattern, then reads the source to understand every branch. It uses write or edit to add characterization tests that match the existing style — including Conjured item tests that will deliberately fail. It runs npm test to confirm the tests actually execute.

The verifier then runs the tests independently and produces a structured summary: 22 passed, 6 failed, here are the failure names and expected-vs-actual values. Clean signal, no noise.

The implementer gets that summary — not raw Jest output. It uses read to open the source, uses edit to make targeted changes, uses bash to run npm test after each edit. With 3.3B active parameters, it generates code fast. The RL training on execution loops means it naturally falls into an edit-test-fix cycle rather than writing a long explanation.

Round 2+: The test writer re-reads the current state, finds coverage gaps the implementer's refactoring might have exposed, and adds more tests. The verifier confirms what's passing and failing. The implementer gets the new summary and iterates.

Final: The reviewer reads everything cold — source, tests, test output. It's checking things the other agents can't objectively evaluate about their own work: Is the refactored code actually cleaner? Did the test writer miss any requirement branches? Is the Item class still untouched?

Each pi -p invocation is a separate session — no shared memory, no shared context. The only communication channel between agents is the filesystem and the verifier's summary. The test writer leaves tests on disk. The verifier reads them and produces structured output. The implementer reads that output and leaves modified source on disk. It's adversarial by construction because each agent only sees the artifacts the others left behind, not their reasoning.

What We Learned the Hard Way

We burned through several iterations before this worked reliably. These are the failures that shaped the final design:

GLM-4.7-Flash writes great tests but can't close. Dense 30B models reason deeply but the reasoning doesn't translate into tool use. GLM would analyze a failing test, explain exactly what needed to change in the source, format it as a markdown code block... and never call edit. The Qwen3 Coder's RL training on execution loops makes it actually use the tools.

Without the verifier, the implementer flounders. Raw Jest output is too noisy for a 3.3B-active model. It would read 80 lines of stack traces and either pick the wrong thing to fix or get overwhelmed and start explaining instead of editing. The verifier distills that down to actionable signal.

"Read the existing file first" is the single most important instruction. Without it, the test writer invents its own import style (ES modules in a CommonJS project), Jest crashes before any test runs, and the orchestrator thinks everything passed because it found zero failures in the output. Matching the existing codebase patterns has to be step 1, not an afterthought.

"Do not explain" has to be the first thing the model reads. Local models default to helpful assistant mode. If the prompt starts with the task description, the model starts explaining. If it starts with "You are a coding agent. Use your tools. Do not explain," the model starts tool-calling. Framing before content.

Check for "passed" not for the absence of "failed." If Jest crashes on a syntax error, there are no test failures to detect — there are no test results at all. The orchestrator has to positively confirm that tests ran and passed, not just check that nothing failed.

Tuning for Your Hardware

If you have 64GB unified memory: Pull qwen3-coder-next (52GB). Same RL training philosophy, but 80B total parameters and trained on 800K executable tasks. It's the best local coding agent model available.

If you only have 16GB: Drop to qwen2.5-coder:7b (4.7GB). Dense 7B, handles the Gilded Rose fine. Token generation will be faster but reasoning on edge cases will be shallower.

If you want multi-model diversity: Use glm-4.7-flash for the test writer (deep reasoning, thorough tests) and qwen3-coder:30b for the implementer and verifier (RL-trained tool use). Both are 19GB but they can't coexist in 32GB, so you'll eat a 5-10 second swap each handoff. Worth it for batch runs, not for live demos.

If tool calling breaks: Reduce the prompt length. Local models degrade faster than frontier models as context fills up. If an agent stalls, check the log — it's probably writing prose instead of calling tools. The "Do not explain" framing helps but isn't bulletproof.

Why This Matters

The adversarial loop is the important part, not the kata.

Most AI coding workflows are single-agent: one model context, one perspective, one prompt that tries to do everything. That works for straightforward tasks. But legacy code — the kind that actually pays the bills — benefits from decomposition. A test writer that can only touch test files. An implementer that can only touch source. A verifier that can only read. A reviewer that judges the whole thing cold.

You don't need different models to get adversarial behavior — you need different mandates. The constraints force genuine disagreement even when the same weights are behind every response. It's the same reason a red team exercise works even when the red team and blue team are from the same company.

You can build this loop for any refactoring task, any codebase, any language. Swap the agent prompts. Swap the model. Swap the test runner command. The orchestrator doesn't care.

And because it's all local, you can run it against proprietary code without sending a single line through someone else's servers. That's not a philosophical point — it's a compliance requirement for a lot of the codebases that actually need this kind of work.

What We'd Do Differently Next Time

Add a git commit between rounds. Right now if the implementer makes a mess, you have to manually revert. Wrapping each round in git add -A && git commit -m "round $ROUND" gives you a clean rollback point.

Pipe the reviewer's output back into the loop. The current script is linear — reviewer goes last and that's it. A more aggressive version would feed the reviewer's FAIL output back to the test writer as round N+1 input, creating a true closed loop.

Try different models per role. The single-model setup here is optimized for reliability and zero swap overhead. Once you're comfortable with the loop, experiment with mixed model setups — a dense model for test writing, an MoE for implementation, a different family for review. The orchestrator makes this a one-line change per agent.

Scale the context window. If you're applying this to a larger codebase, consider setting num_ctx higher in a custom Ollama Modelfile. Qwen3 Coder supports 256K natively, but Ollama defaults conservatively. More context means the agents can see more of the codebase per turn.
