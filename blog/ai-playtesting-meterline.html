Teaching an AI to Play My Game, and Learning How to Test the AI

I gave a local AI the controls to my shooter. It found the wall just fine.

Local Models AI Playtesting Agent Evaluation

I'm building METERLINE, a scrolling shooter. I want to know whether the player gets enough firepower to keep up with the difficulty.

Testing that means replaying the opening after every change. Dying doesn't tell me whether the enemies were too tough, the upgrades were too scarce, or I just played like an idiot.

So I built a local AI playtesting harness to put in some laps and log the results. Then I changed the prompt to get the pilot moving more. It started driving into the bottom barrier. Repeatedly.

Well, hell. Now I've got two things to debug.

Handing Over the Controls

The harness runs the Phaser game in Chromium, reads structured engine state, and passes movement and purchase decisions back through the game's controls. The model doesn't read screenshots.

A scripted pilot gives me a baseline. A Kev adapter connects the local model, with cautious, aggressive, and collector styles to vary its priorities.

I set a starting seed and a time budget. Reports capture damage locations, decisions, inference latency, and every time the harness intervenes or falls back to scripted control.

Putting It to Work

Two processes do the work: a Python model server and a Node runner that controls the game.

With Kev and its serving dependencies installed in a Python environment, the model-server command is:

python -m kev.serve \
  --run jaredpalmer/kev-0.8b \
  --port 8009

This loads the checkpoint and serves requests on port 8009. The first launch downloads the weights into the local Hugging Face cache. Leave it running while the game runner uses it.

The runner checks that Kev is available, starts Vite, and launches an isolated Chromium session through Playwright. Here's the setup, with logging and some browser settings omitted:

import { createServer } from 'vite';
import { chromium } from 'playwright';

// Inside the runner, after parsing arguments and checking Kev:
server = await createServer({
  server: { host: '127.0.0.1', port: 0, hmr: false },
  clearScreen: false
});
await server.listen();
const url = server.resolvedUrls.local[0];

browser = await chromium.launch({
  headless: !values.headed,
  args: [
    '--disable-background-timer-throttling',
    '--disable-renderer-backgrounding'
  ]
});
const context = await browser.newContext({
  viewport: { width: 960, height: 540 },
  serviceWorkers: 'block'
});
const page = await context.newPage();
await page.goto(`${url}?harness=1`);
await page.waitForFunction(
  () => window.__ML_TEST?.ready(),
  undefined,
  { timeout: 30000 }
);

Port 0 lets Vite use an available port. The model server stays on 8009. In development, ?harness=1 enables the custom window.__ML_TEST hooks: start() begins an attempt, observe() reads state, and act() applies controls.

The runner observes, asks Kev for a decision, checks fresh state, applies the action, and logs it. It saves an HTML report, JSON results, and a decision trace, then shuts down the game server and browser.

For a short test, I use Kev on level 1 with the cautious style, seed 12345, and a visible browser. A 60-second budget limits elapsed test time. If an attempt ends early, the runner starts another with the next seed.

The Game Doesn't Wait for Inference

The game doesn't give a damn that the model is still thinking. Enemies move and terrain scrolls. A clear path can disappear before the answer comes back.

The barrier collisions made me check both the movement's duration and the age of the observation behind it. A valid response can still be a bad move.

Keeping It Out of the Ditch

I trimmed the observations to relative positions, nearby threats, pickups, equipment, and recent decisions. Then I added terrain and boundary checks for the one second each movement command lasts.

The model chooses from the remaining actions. After inference, the harness checks the choice against fresh state. I record blocked movements and scripted fallbacks. If I have to keep grabbing the wheel, that belongs in the report.

Check the Whole Second

This function filters the movement choices. directions maps the nine movement names to their descriptions.

export function movementCandidates(world) {
  const axes = {
    stay: [0, 0], up: [0, -1], down: [0, 1],
    left: [-1, 0], right: [1, 0],
    upLeft: [-Math.SQRT1_2, -Math.SQRT1_2],
    upRight: [Math.SQRT1_2, -Math.SQRT1_2],
    downLeft: [-Math.SQRT1_2, Math.SQRT1_2],
    downRight: [Math.SQRT1_2, Math.SQRT1_2]
  };
  const safe = Object.entries(directions).filter(([id]) => {
    const [dx, dy] = axes[id];
    for (let step = 1; step <= 10; step++) {
      const t = step / 10;
      const x = world.ship.x + dx * world.ship.speed * t;
      const y = world.ship.y + dy * world.ship.speed * t;
      if (
        x < world.bounds.minX || x > world.bounds.maxX ||
        y < world.bounds.minY || y > world.bounds.maxY
      ) return false;
      if (world.terrain.some(r => {
        const left = r.x - world.scrollSpeed * t;
        const nx = Math.max(left, Math.min(x, left + r.w));
        const ny = Math.max(r.y, Math.min(y, r.y + r.h));
        return Math.hypot(x - nx, y - ny) < world.ship.radius + 4;
      })) return false;
    }
    return true;
  });
  return Object.fromEntries(
    safe.length ? safe : [['stay', directions.stay]]
  );
}

The check samples ten positions over one second, accounting for terrain scrolling toward the ship. It rejects paths that cross the bounds or pass within four pixels of a terrain collision.

It assumes constant scroll speed and known terrain. It doesn't dodge enemies and can miss collisions between samples. If every direction fails, it offers stay, which may still be unsafe.

Check Again Before Applying It

After inference, the runner checks again. End-of-run, upgrade-menu, and fallback handling are omitted here:

const fresh = await page.evaluate(
  () => window.__ML_TEST.observe()
);

// End-of-run, upgrade-menu, and fallback handling omitted.

if (
  values.controller === 'kev' &&
  fresh.cards.length === 0 &&
  !Object.hasOwn(
    movementCandidates(fresh.observation.world),
    decision.action.direction
  )
) {
  decision = {
    ...decision,
    requestedDirection: decision.action.direction,
    action: { ...decision.action, direction: 'stay' }
  };
  current.safetyInterventions++;
}

await page.evaluate(
  d => window.__ML_TEST.act(d.action, d.pick),
  decision
);

A blocked move becomes stay. The trace preserves the requested direction, and the report counts the intervention so I can distinguish the model's choice from the harness's correction.

Four kills and no damage. I'll take it, but 28 seconds doesn't establish level completion, better play than the baseline, or better game balance.

The two scripted fallbacks and two blocked movements matter just as much. This is a result for the model with assistance.

What I Need From the Logs

To tune the game, I need the logs to answer a few questions:

  • Difficulty: Where do attempts end, relative to how many reached each section? A late encounter with fewer deaths may simply have fewer arrivals.
  • Progression: How long until the first purchase, and how long between later purchases?
  • Readiness: What equipment and defenses remain at key checkpoints?
  • Enemy pressure: Which enemies and attacks cause damage, and how long do those enemies survive?
  • Reward access: Are pickups scarce, hard to reach, or being ignored by the controller?
  • Controller quality: Are latency, fallbacks, or safety interventions distorting the result?

Some of that is logged already. Exact purchase events, bullet-source attribution, and more encounter detail still need wiring up.

Change One Thing, Run It Again

Next I'll freeze the controller, run the opening minute across several fixed seeds, change one spawn or reward parameter, and run those seeds again.

I'll compare damage, progress, and harness interventions, adding purchase timing and checkpoint equipment when those events are logged. Changing the pilot and level together would make the results harder to explain.

Even with the same seed, inference timing varies. Repeated runs should help show how much variation comes from the controller.

Nobody Is Training a Model Here Yet

I'm evaluating a pretrained model, adjusting its observations, prompts, and controls. I haven't implemented training. Giving it 15 minutes means 15 minutes of testing; it doesn't learn from those runs.

Demonstrations or fine-tuning may come later, once I can measure whether they help.

I still need human playtesters. The bot gets engine state and help avoiding terrain. People get a screen and their reflexes. Bot runs can flag trouble spots, but they can't tell me whether the game is any damn fun.

Next time it hits a wall, I want the logs to tell me whether to fix the level or the pilot.
