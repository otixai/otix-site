Directing Agents to Test, Part 2: API Acceptance Tests

Turn a requirement into API tests that catch wrong permissions and unwanted side effects.

Agentic Engineering Testing Spec-Driven

Following Part 1, I'll give an agent one rule to verify: only an administrator of the target workspace may invite a member. A denied request must save no invitation and queue no delivery.

Define the Cases

This example uses 201 for success, 401 for missing authentication, and 403 for insufficient permission. Adapt these to your API's contract.

  • Admin in the target workspace: create the invitation and queue one delivery.
  • Ordinary member: deny, with no side effects.
  • Admin only in another workspace: deny, with no side effects.
  • No session: reject, with no side effects.

Ask the agent to flag undefined rules for duplicates, existing members, and permitted roles. Don't let it invent expected behavior.

Give the Agent Clear Boundaries

Test the four invitation cases above.
Use existing test commands and fixtures.

Send HTTP requests through the running application.
Keep authentication, authorization, and persistence real.
Use an isolated database with the application schema.
Replace delivery with a recording queue adapter.

Start each test with fresh accounts, workspaces, and
an empty queue recorder. Always clean up, even on failure.
Assert the response, saved invitations, and queued jobs.
Do not mock the permission decision or send real emails.

The real database adds integration coverage. The queue recorder verifies submission, not email delivery.

Test the Cross-Workspace Denial

Give the agent this pseudocode to adapt to existing fixtures. The caller must belong only to workspace A.

test "denies an admin from another workspace":
  with isolated_application_and_database() as app:
    a = app.fixtures.workspace()
    b = app.fixtures.workspace()
    caller = app.fixtures.admin_of(a)
    session = app.fixtures.authenticated_session(caller)

    assert app.invitations.for_workspace(b) == []
    assert app.delivery_queue.recorded_jobs == []

    response = app.http.post(
      "/workspaces/" + b.id + "/invitations",
      session=session,
      json={"email": "new@example.test", "role": "member"}
    )

    assert response.status == 403
    assert app.invitations.for_workspace(b) == []
    assert app.delivery_queue.recorded_jobs == []

The request uses the public interface; helpers inspect persisted state. Checking only 403 would miss a handler that saves an invitation before denying access.

This example assumes writes and queue submission finish before the response. For an outbox or background worker, inspect committed outbox state and drive pending work to a defined completion point. An immediate empty-queue check can miss delayed side effects.

Verify Success and Failure

A server that rejects everything passes the denial tests. Add the allowed case: verify 201, a returned ID matching the saved invitation, the correct workspace, recipient, and role, and one delivery referencing that invitation.

Then ask the agent to demonstrate that the tests catch the defect:

In an isolated checkout, temporarily allow admins from
any workspace. Confirm the cross-workspace test fails
on the expected behavior, not a setup error.

Also confirm the allowed case fails if all requests
are denied. Restore the correct code and rerun the suite.
Keep temporary faults out of the final diff.

If the denial test stays green, check for a caller in both workspaces or a mock bypassing authorization. For an existing bug, use the broken revision to demonstrate the regression instead.

Review the Evidence

I want the final code state, exact commands, test counts and results, observed fault failures, and skips or blockers. Review the diff for weakened assertions and unexpected mocks.

State the limits: these tests cover authorization, persistence, and queue submission. Browser behavior, email delivery, and concurrent requests still need their own checks.
